## 1. Observable goal

Add reusable repository memory that converts selected completed delivery evidence into small, versioned, reviewable records; keeps curated repository documentation and source files authoritative; builds a compact machine-local index deterministically; and retrieves a bounded set of relevant records by repository, work, stage, path, and topic with explicit provenance.

The delivered behavior must make stale, conflicting, superseded, redacted, expired, corrupt, or missing records visible and deterministic. Rebuild and repair must reproduce or quarantine derived state without silently changing curated repository truth. Supervisor status may report non-authorizing memory health/count summaries, but memory data, index entries, status output, or promotion metadata must never issue, reconstruct, rotate, or broaden workflow, lease, reservation, mutation, provider, or tracking authority.

## 2. Non-goals

- Automatic ingestion of every `docs-ai/` artifact, raw run log, conversation, Linear comment, Git history, or external provider response.
- Vector databases, embeddings, semantic similarity, LLM-based ranking at retrieval time, network search, or a new third-party dependency.
- Treating generated summaries, the machine index, or retrieved text as a normative replacement for repository documentation, source code, `AGENTS.md`, the workflow registry, or `workflow.json`.
- Allowing arbitrary agents to promote their own run evidence, bypass the documentation stage, or use a role string as write authority.
- Mutating completed/historical workflow artifacts, rewriting curated records in place, deleting protected delivery evidence, or auto-resolving substantive conflicts.
- Adding a new queue-selection, Linear, notification, Git publication, merge, or autonomous capability surface.
- Loading the detailed memory schema/index into the healthy autonomous prompt; retrieval results remain a bounded optional input selected by deterministic code.

## 4. Proposed architecture and authority model

Use two deliberately unequal tiers.

### 4.1 Repository-owned curated record tier

Add repository conventions for immutable record versions under `docs/repository-memory/records/` and immutable atomic-batch commit markers under `docs/repository-memory/commits/`. Each record is named from a canonical record ID plus version (for example, `<record-id>.v0001.json`); each marker is named `<batch-promotion-id>.json`. A record is committed and eligible only through one valid marker whose complete ordered target/digest set contains it. A small `docs/repository-memory/README.md` explains curation, authority, lifecycle, commit-marker recovery, and review. These files are ordinary reviewed repository changes governed by the active delivery entry, reservation, and `AuthorizeMutation`; the memory package never mints write authority.

Curated records are navigation and compact reusable knowledge. Their claims must point to one or more authoritative repository-relative sources (`AGENTS.md`, curated Markdown, source, schema, or an exact completed workflow artifact) with content digests. A record may contain a concise normalized summary and closed metadata, but retrieval must return the provenance beside it and must state that the referenced current repository source wins if the summary and source differ.

Completed `docs-ai/` evidence is an eligible promotion input, not an automatically trusted reusable source. Promotion creates a new reviewed record and, when durable behavior needs documentation, updates or references the nearest curated page; it never edits the completed evidence.

### 4.2 Machine-local derived index tier

Store the generated compact index beneath the existing repository state home, for example `repository-memory/index.json`, plus quarantined diagnostics under `repository-memory/quarantine/`. The index is a cache/projection only. It contains canonical keys, source digests, lifecycle state, compact retrieval fields, and record-file references—not raw artifacts, full source documents, secret-bearing content, authority references, or copied patches.

Build it from the repository-owned commit-marker set and each marker's complete validated record set under `allocation.lock` using `StatePathGuard`, atomic replacement, readback, and a digest over canonical sorted inputs. Unmarked record files are never index inputs. Index absence, lag, or corruption must never change curated files: explicit rebuild persists a replacement, while query may construct the same complete marker-derived projection transiently in memory without mutating state home. A valid index records the repository ID/key, exact source-tree identity, and committed-marker-set digest used to build it so another repository, linked worktree, or older commit set cannot reuse it accidentally.

## 5. Contracts and data model

Add version `1.0` schemas under `src/skills/linear-delivery-loop/references/` and mirror every non-portable invariant in `scripts/contracts.py`.

### 5.1 `repository-memory-record.schema.json`

One strict, additional-properties-false record includes:

- immutable identity: `schemaVersion`, `recordId`, positive `recordVersion`, stable `candidateId`/`candidatePromotionId`, `repositoryId`, `repositoryKey`, canonical record filename, `candidateIntentSha256`, `promotionManifestPayloadSha256`, and `recordPayloadSha256` as defined by the acyclic projections in §5.5; the final record-file digest is deliberately absent from the record;
- classification: closed `kind` (concept, decision, how-to, runbook, troubleshooting, constraint, or reference), normalized sorted `topics`, `paths`, applicable delivery `stages`, and optional exact `work` binding (`workflowId`, `workKey`, provider/external ID);
- compact content: display-only title limited to 160 Unicode scalar values, display-only summary limited to 2,000, and zero to 16 structural keyed assertions defined below; at most 16 topics of 64 each, 32 repository-relative paths, and 16 provenance sources; no full artifact body or patch. Title/summary never participate in conflict, duplicate, confidence, or authority decisions;
- provenance: one or more repository-relative source references containing source kind, path, SHA-256 content digest, optional workflow/artifact stage, workflow ID/work key, and an exact anchor when the source format supports one;
- creation/update provenance: exact-key `createdBy` and `updatedBy` objects containing UUID curation workflow ID, stable UUID per-candidate promotion ID, `promotionManifestPayloadSha256`, fixed producer `docs-as-code`, existing-format repository ID, 40/64-hex head SHA, SHA-256 physical-worktree fingerprint, and RFC 3339 observed timestamp. Version 1 requires equality; later versions preserve `createdBy` byte-for-byte and replace `updatedBy` with the successor candidate-promotion identity. These closed, bounded values are stable evidence identities, not people, credentials, or authority.
- confidence is a provenance-topology class, not machine proof that prose is true: active records use `current-source-bound`, `source-evidence-bound`, or `legacy-evidence-bound`; archived/redacted content-free successors require `not-applicable`. Runtime validation proves only the structural source binding below; documentation review owns semantic correctness. `legacy-evidence-bound` is excluded from default retrieval/context and is visible only through diagnostics or an explicit manual query flag.
- freshness policy: fixed `digest-on-read`, complete source digests, and optional `reviewAfter`; the index derives `fresh`, `stale`, `review-due`, or `expired` from current sources and the injected clock without mutating the record.
- lifecycle: `active`, `archived`, or `redacted`; creation/review timestamps; retention class; optional expiry; append-only `supersedes` predecessor identities; optional `restores` archived predecessor identity; and redaction reason/digest metadata without removed content. `active` requires title/summary and one to 16 assertions; `archived` permits only a safe title plus archive reason and no summary/assertions, and `redacted` permits no title/summary/assertions. `superseded` is a derived index state, never a mutable field on an immutable predecessor.

Each assertion is an additional-properties-false object with:

- one normalized key matching `^[a-z][a-z0-9]*(?:[._-][a-z0-9]+){0,7}$` and at most 128 characters; keys are unique within a record;
- `valueType` of `string`, `integer`, `boolean`, or `string-set`, fixed comparison `equals`, and one typed value. Strings are NFC-normalized, Unicode-trimmed, and have internal Unicode whitespace runs collapsed to U+0020 while preserving case; integers are JSON integers in `[-9007199254740991, 9007199254740991]`; booleans are native JSON booleans; string-set members use string normalization, are unique, and sort by Unicode code point;
- one to eight `provenanceRefs` resolving to record provenance IDs. `current-source-bound` requires all refs to current non-`docs-ai` sources; `source-evidence-bound` requires at least one current non-`docs-ai` source and at least one exact completed current/legacy delivery artifact; `legacy-evidence-bound` requires only explicitly selected legacy completed evidence. Assertion confidence is derived from those categories, and record confidence equals the weakest assertion class in the order shown.

The docs-owned manifest supplies the reviewed assertion-to-source mapping. Runtime never parses title, summary, source prose, or model output to decide semantic support; it validates only keys, typed normalized values, scopes, source categories, identities, and digests.

Runtime parity additionally enforces NFC/case-fold-safe paths and IDs, rejects lone surrogate code points, requires stable sorted unique arrays, record ID/version/filename agreement, repository binding, digest syntax, exact `createdBy` preservation, closed confidence evidence, no source outside the repository or exact registered workflow folder, no secret-like key/value, lifecycle cross-field rules, and the complete append-only graph rules in §8.

### 5.2 `repository-memory-promotion.schema.json` and canonical artifact ownership

Add one version `1.0` durable promotion-provenance contract as an optional canonical workflow artifact named `<date>-<slug>-memory-promotion.json`.

- **Owner/producer:** `$docs-as-code` is the canonical artifact owner and the only producer value is `docs-as-code`. `src/skills/goal-to-delivery/references/artifact-contract.md` must add this optional artifact type and ownership explicitly. The existing safe relative-path `artifactInventory` shape already accepts the filename; semantic promotion/descriptor tests require exact membership without a descriptor schema-version bump or a new mandatory field.
- **Storage/inventory:** promotion always runs in a distinct registered curation workflow whose workflow ID differs from every completed source workflow. The manifest lives in that curation workflow folder under `docs-ai/`, is listed in its `artifactInventory`, and each resulting record binds its acyclic `promotionManifestPayloadSha256` rather than the manifest's final file digest. It is not stored in or retrofitted onto a source workflow, the state-home index, a completion payload, or a publication attestation.
- **Shape:** immutable curation workflow/repository/head/worktree identity, producer, created timestamp, exact source workflows/artifacts and digests, closed `compatibilityClass` (`current-completion-v2` or `legacy-completion-v1`), stable UUID `batchPromotionId`, and a `decision` of `promotion-approved` or `no-candidates`. `promotion-approved` contains one to 32 candidates sorted by ascending canonical lowercase UUID `candidateId`; each has a distinct stable UUID `candidatePromotionId`, exact target record ID/version/path, full record intent (classification, display content, assertions, confidence, provenance, freshness, lifecycle/retention, predecessors), and `candidateIntentSha256`. Approval is input, not completion; only a valid repository commit marker establishes promotion, and journal/result may report or reconstruct `promoted` from it. `no-candidates` requires an empty candidate array plus a closed reason code and summary of at most 500 Unicode scalar values; its batch ID is the idempotency identity for the no-op result.
- **Manual and semi-autonomous validation:** resolve the curation workflow through the registry, require its current artifact stage to be `docs` or `completion`, require the manifest in its inventory, verify repository/head/worktree and every source digest, and validate the normal reservation/mutation authorization independently before either manifest or curated record is written.
- **Autonomous validation:** apply the same checks and additionally bind the manifest to the engine-owned passed `docs` publication/checkpoint attestation at the exact head. The attestation proves the autonomous docs gate; the manifest supplies memory-specific candidate decisions and digests.
- **Source workflow validation:** a current source workflow must be exact-registered and completed. An earlier current-layout completed workflow or explicitly selected historical folder that predates this artifact remains eligible only as read-only source evidence under `compatibilityClass: legacy-completion-v1`; the new curation workflow owns the manifest. A prior completed workflow is never retrofitted or rewritten. Historical fallback is explicit, records the selected path/digests, and yields `legacy-evidence-bound` confidence until a current curated source is added.
- **Zero-candidate behavior:** every curation docs stage that evaluates promotion may write exactly one `no-candidates` manifest. It is valid durable evidence, produces no record/index entry, and makes identical replay idempotent.
- **Non-authority semantics:** producer, role, manifest, candidate, record, digest, and status fields are evidence only. They cannot satisfy or replace lease, reservation, `AuthorizeMutation`, publication, provider, tracking, issue selection, or completion authority; validators accept no raw/opaque authority fields.

### 5.3 `repository-memory-commit.schema.json` and `repository-memory-index.schema.json`

The repository-owned commit marker is an immutable, additional-properties-false canonical file containing schema version, repository ID/key, `batchPromotionId`, `promotionManifestPayloadSha256`, `promotionBatchRequestSha256`, and one complete array in canonical candidate order. Every member binds `candidateId`, `candidatePromotionId`, exact target record path, `candidateIntentSha256`, `recordPayloadSha256`, and final `recordFileSha256`. The marker adds `batchCommitPayloadSha256` from §5.5; its own final file digest is absent from the marker and appears only in derived index/journal/result evidence. An empty or partial target set is invalid, a target may belong to only one valid marker, and any ID/path/digest mismatch invalidates the entire marker-bound batch. The marker is completion evidence for repository memory only; it grants no workflow, Git, publication, reservation, or mutation authority.

The index contains schema/revision, repository binding, build ID/time, canonical input digest, deterministic builder version, the canonical sorted marker path/payload/file digest set, sorted compact entries, conflict/stale/quarantine summaries, and counts by lifecycle. Each entry holds its owning batch marker plus only the fields needed to filter/rank and its record path/digest/provenance digests. The complete marker and record must be reread and revalidated before return so a stale index cannot smuggle changed or incompletely committed content.

### 5.4 Promotion and query request/result contracts

Define strict atomic-batch promotion request/result, query, retrieval result, and context-envelope contracts. A promotion request identifies one exact manifest, its `batchPromotionId`, the deterministic commit-marker target path, the complete ordered candidate ID/promotion ID/record-target set, expected prior index input digest, and one already-issued mutation authorization whose sorted scope equals the union of every record target and that one marker target exactly. Selected subsets, missing/extra paths, and directory wildcards are forbidden. A completed result contains the batch identity/request digest, manifest payload/file digests, commit-marker payload/file digests, one ordered result per candidate with intent/payload/final-file digests and `promoted` outcome, and the committed index digest or a closed `index-reconstruction-required` diagnostic when the repository commit succeeded but derived-state repair remains; results never report partial committed success. Queries require exact repository identity, `maxRecords`, `maxCharacters`, and `maxBytes`, and permit at most one work filter, one stage filter, 32 path filters, and 16 topic filters using the record-field length limits. Retrieval results include query digest, committed-marker-set/index/source digests, deterministic ordering/rank reasons, item/character/byte accounting, complete provenance, and count-only exclusion/warning summaries for stale, conflict, superseded, archived, redacted, expired, legacy-evidence-bound, oversized, or quarantined records.

No contract accepts a raw capability, nonce, reservation control, caller-chosen state-home output path, arbitrary glob, absolute source path, ranking callback, free-form command, or secret-bearing content.

### 5.5 Acyclic canonical digest projections

All hashes use the existing canonical JSON convention: recursively sorted object keys, original array order, compact separators, UTF-8 over `ensure_ascii=true` JSON, and SHA-256 rendered as lowercase `sha256:<64-hex>`. Each named projection is an exact additional-properties-false value; no digest ever hashes itself or a value that depends on it.

1. **`CandidateIntentV1`** is the complete manifest candidate excluding only `candidateIntentSha256`. It includes candidate/candidate-promotion IDs, target identity/path, content/assertions, source bindings, confidence/freshness/lifecycle/retention, and predecessors. `candidateIntentSha256 = SHA256(CanonicalJSON(CandidateIntentV1))`.
2. **`PromotionManifestPayloadV1`** is the complete manifest excluding only `promotionManifestPayloadSha256`. Candidate entries include their intent fields and already computed intent digests. It contains no record payload digest, record-file digest, journal field, batch result, or index result. `promotionManifestPayloadSha256` hashes that projection. The immutable manifest file then adds this one digest; `promotionManifestFileSha256` hashes the complete canonical file and is stored only in the promotion journal/result, never in a record or in the manifest payload.
3. **`RecordPayloadV1`** is constructed after the manifest payload digest is known. It contains the candidate intent fields plus `createdBy`/`updatedBy` referencing `candidatePromotionId` and `promotionManifestPayloadSha256`, and excludes only `recordPayloadSha256`. The record adds `recordPayloadSha256 = SHA256(CanonicalJSON(RecordPayloadV1))`. `recordFileSha256` hashes the final canonical record file including `recordPayloadSha256` and is stored only in the downstream commit marker and derived journal/result/index evidence.
4. **`PromotionBatchRequestV1`** contains batch ID, manifest payload/file digests, deterministic marker target, ordered candidate/candidate-promotion IDs, record target paths, candidate-intent digests, expected prior index digest, repository/head/worktree identity, and the consumed authorization identity/digest whose exact scope is all record targets plus the marker target. It excludes mutable journal phase, record/marker payload or file digests, index result, and final result. Its hash is the immutable replay key.
5. **`BatchCommitPayloadV1`** is constructed only after every final record byte string and digest is known. It is the complete commit marker excluding only `batchCommitPayloadSha256`; it binds repository identity, batch identity, manifest payload digest, batch-request digest, and the complete ordered candidate/promotion ID, target, intent, record-payload, and record-file digest set. The marker adds `batchCommitPayloadSha256 = SHA256(CanonicalJSON(BatchCommitPayloadV1))`. `batchCommitFileSha256` hashes the complete canonical marker and is stored only in derived index/journal/result evidence, so no digest cycle is introduced.
6. **`IndexSemanticV1`** is the complete index excluding `indexSemanticSha256` and `builtAt`; it contains the canonical marker path/payload/file digest set, canonical sorted marker-owned record target/payload/file digests, and derived lifecycle/graph/conflict state. The stored index adds `indexSemanticSha256`; its final `indexFileSha256` is journal/result evidence and is not embedded. **`RetrievalQueryV1`** is the complete query and produces the query digest; **`RetrievalResultV1`** embeds that query digest but has no self/result digest or timestamp. **`ContextEnvelopePayloadV1`** is the complete escaped envelope excluding only `contextPayloadSha256`; the tool content adds that digest.
7. **`ContextDeliveryAccountingV1`** is the exact final `ContextDeliveryV1` projection used for usage accounting, with `accounting.charactersUsed` and `accounting.bytesUsed` replaced by the fixed six-ASCII-digit sentinels `"000000"`; no other field is excluded or replaced. `ContextDeliveryV1` is the complete fixed developer/tool message bundle, has no self digest or timestamp, and stores both usage values as zero-padded six-digit decimal strings. Because requested/repository maxima are below 100,000, replacing each sentinel with its computed six-digit value cannot change serialized length. The final canonical serialization must equal those reported inclusive counts exactly or fail closed.

The validator reconstructs `CandidateIntentV1` from each record, proves equality with the manifest intent digest/target identity, then independently verifies record payload/final-file and commit-marker payload/final-file digests. Fixed known-answer fixtures publish exact canonical byte strings and expected hashes for a one-candidate manifest, its record, batch request, commit marker, result, index, envelope, and delivery accounting projection; single-field tampering at every layer fails, while exact construction/replay returns byte-identical hashes/results.

## 6. Promotion flow, concurrency, and crash recovery

Promotion is one atomic ordered batch per `batchPromotionId`, including the one-candidate case. Its state-home directory contains `repository-memory/promotions/<batch-promotion-id>/journal.json`, engine-owned prepared files while nonterminal, and immutable terminal `result.json`; these are recovery aids and derived evidence, never commitment authority. The sole recoverable commit point is the successful create-new, flush, and exact readback of `docs/repository-memory/commits/<batch-promotion-id>.json`. Before that point none of the batch is visible; after it the complete marker-bound batch is committed even if journal, result, or index is absent or corrupt. Every candidate also carries stable `candidateId` and `candidatePromotionId`. Same batch ID plus the same `PromotionBatchRequestV1` returns the exact recorded or marker-reconstructed result. Reuse of any batch, candidate, or candidate-promotion ID with changed data is `conflicting-replay` and writes nothing.

Lock order is fixed: the caller first obtains an issued ordinary reservation and one exact-path mutation authorization whose `targetOperationId` equals `batchPromotionId` and whose sorted scope equals all one to 32 target record paths plus the one deterministic commit-marker path—no missing or extra path and no directory wildcard. Promotion then acquires only the canonical repository `allocation.lock`. Under that mutex it uses an explicit unlocked supervisor primitive to revalidate/consume the authorization while atomically persisting the `prepared` batch journal. Promotion, query, rebuild, and repair serialize on this same mutex; status takes only a read snapshot and never rebuilds. The critical section never nests/reacquires the mutex, obtains another authority lock, performs network/provider work, launches Git mutation, or invokes a callback.

1. Before locking, resolve curation/source workflows and validate the complete manifest, digest projections, all candidates, graph/assertion rules, completed evidence, redaction, distinct IDs/targets, canonical candidate ordering, and issued exact-scope authorization. `no-candidates` validates and returns one durable idempotent no-op result without mutation authorization or a promotion journal.
2. Under the mutex, reread every input and current record/marker/index/journal. Validate the whole batch again as one prospective graph: the marker target and every record target are absent, target versions are current, predecessor dependencies refer either to existing terminals or earlier candidates in canonical candidate order, and no two candidates duplicate/conflict/branch. Any preflight conflict fails the entire batch before authorization consumption or target creation; subsets are never attempted.
3. Atomically consume the exact authorization and persist `prepared` with `PromotionBatchRequestV1`, ordered candidates/record targets/marker target, prior index digest, and intended payload digests. Serialize every final record to a distinct engine-owned prepared file, derive and serialize the complete commit marker after their final digests are known, and prepare the next complete index projection under that batch's state-home directory. Flush/read back all prepared bytes before creating any repository target. No unauthorized temporary path is created in the repository.
4. Compare-create record targets in canonical candidate order with OS create-new/no-clobber semantics (`O_CREAT|O_EXCL`/Windows `CREATE_NEW`), write the already prepared exact bytes, flush, and read back. Before each create, journal `creating:<candidateId>`; after success, journal its payload/file digest. A crash-partial record is removable only when the journal proves pre-absence/create intent and its bytes are an exact prefix of the prepared bytes; any other mismatch protects the batch. No replace/overwrite fallback is allowed. The batch remains uncommitted and is excluded from index/retrieval until the marker commit point; no index publication occurs per candidate.
5. After every record readback and the prepared index readback pass, compare-create the exact prepared commit marker with the same create-new/no-clobber, flush, and readback requirements. The durable presence of that complete valid marker, confirmed by readback during the original run or by full validation during replay, is the single commit point. A marker is valid only if its manifest/request identity and complete ordered record target/digest set all validate; retrieval never exposes a strict subset. A crash-partial marker remains pre-commit and is removable/retryable only when the intact journal proves marker pre-absence/create intent and its bytes are an exact prefix of the prepared marker; otherwise it protects the batch. Marker creation failure leaves the batch uncommitted unless the existing marker is byte-identical and its entire bound set validates, in which case replay recognizes the already committed batch.
6. Still under the mutex, atomically replace/read back the derived index with the prepared full committed-marker projection, then persist/reconstruct one `committed` journal/result with ordered per-candidate `promoted` entries and marker/index digests. Index and result failure after marker creation does not undo or hide the committed repository batch: it records or reconstructs `index-reconstruction-required`, and the next query/rebuild derives the complete projection from markers. After terminal-result readback, delete only engine-owned prepared files and retain their hashes in state-home evidence. There is no successful partial result.
7. If deterministic failure occurs before marker creation, remove only record targets whose batch ownership, pre-absence, create intent, and exact complete/prefix bytes are proven by the intact journal/prepared file, plus engine-owned state-home prepared files; verify target absence and return one failed result with every candidate uncommitted. If ownership/removal proof is ambiguous, protect the batch and require attended recovery. Once a valid marker exists, rollback is forbidden: all marker-bound records are committed and recovery may only finish derived index/result state or create later reviewed successors.
8. Crash replay is phase-exact: before prepared/consumption, authority remains unconsumed; during preparation, recreate only missing exact state-home files; after record N and before marker, verify created prefixes and continue or safely roll back; after all records and before marker, verify the complete set then create the marker; after marker and before index/result, recognize the marker as committed and reconstruct index/result without new mutation authority. Mismatch at any phase protects or quarantines the whole batch. Exact replay never redistributes authority or changes scope.

Query has exact old-index-or-reconstructably-committed semantics. Under the mutex, an index whose marker-set digest equals the current valid repository marker set may be used. If a crash leaves an older index after a new valid marker, query constructs the complete current marker-derived projection transiently in memory and returns the newly committed batch; it never returns the old index as if current. If an index is ahead, divergent, absent, or corrupt, query ignores it and reconstructs from all valid markers. A malformed marker, duplicate marker ownership, missing bound record, or digest mismatch fails closed for that entire named batch: none of its records are exposed, while independently valid batches may still be returned with a bounded corruption diagnostic. Thus a query racing normal promotion blocks until the critical section ends and sees either the pre-marker old set or the post-marker complete set; a process death immediately after marker creation still yields the complete reconstructable committed set on the next query.

State-home journals/results/indexes are disposable. With a missing or corrupt journal but a valid marker and complete bound records, replay/rebuild treats the batch as committed and deterministically regenerates derived index/result evidence from the marker. A journal claiming committed without a valid marker has no effect. With no marker, crash-created record files are uncommitted orphans: rebuild/query exclude and report them by bounded path/digest diagnostics, never infer batch membership, and never delete them automatically after journal loss. A malformed marker or incomplete/mismatched bound set quarantines the entire named batch and requires attended repair. After total state-home loss, scanning and validating repository commit markers plus their complete record sets is sufficient to rebuild the exact committed index; unmarked records remain excluded.

Cross-process and linked-worktree contenders serialize on repository identity. A competing batch that becomes stale/conflicting after the winner commits fails as a whole, leaving none of its targets. Required fixtures cover canonical batches of 2 and 32, conflict at first/middle/last candidate, dependency ordering, duplicate IDs/targets/assertions, crash at every candidate and marker/index/result boundary, safe pre-marker rollback and protected ambiguity, marker-before-index query races, missing/corrupt journals, total state-home loss/rebuild, same/different-ID concurrency, and replay after commit—with no overwrite, lost version, partial visibility/success, split-brain result, unsafe cleanup, or deadlock.

## 7. Bounded deterministic retrieval

Retrieval is local, read-only, and deterministic:

- Repository binding is always mandatory and exact. Optional filters narrow by exact workflow/work key, delivery stage, normalized repository-relative path (exact or ancestor relationship), and normalized topic.
- Default eligibility is terminal `active`, unexpired, non-stale, non-conflicting, non-redacted, non-archived, and not `legacy-evidence-bound`. Callers may request lifecycle diagnostics but not suppressed content.
- Normalize identifiers/topics with NFC plus case-folding for comparison while retaining canonical display text; reject lone surrogates. Rank, in order: exact work, exact path, closest path ancestor (fewest missing segments), exact stage, descending exact-topic match count, confidence (`current-source-bound`, `source-evidence-bound`, `legacy-evidence-bound`), kind priority (`constraint`, `decision`, `runbook`, `troubleshooting`, `how-to`, `reference`, `concept`), descending logical version, then ascending case-folded `recordId` and canonical filename.
- Query defaults are `maxRecords=8`, `maxCharacters=12000`, and `maxBytes=24576`. Repository maxima are `32`, `48000`, and `98304`; query minima are `1`, `1000`, and `4096`. Records use the field/cardinality limits in §5.1. No caller can exceed these values.
- A character is one Unicode scalar value after NFC. The character charge is the scalar length of the canonical compact JSON serialization of the complete `items` array (`[`/`]`, commas, object keys, metadata, rank reasons, provenance, escaped content, and values included; no whitespace; lone surrogates rejected). Candidate inclusion first enforces item count, then the requested character ceiling.
- The byte charge is the UTF-8 length of the entire final canonical result document, including schema/query/index digests, repository binding, the `items` array, all provenance/rank metadata, and count-only diagnostics/omission fields. After character selection, remove lowest-ranked whole items until the final byte ceiling fits. Never truncate a field or item. If the highest-ranked item alone exceeds either remaining character budget or the final byte ceiling, omit it as `oversized` and continue; if none fit, return a valid empty bounded result. Fixed envelope and aggregate diagnostic counts must themselves fit the 4,096-byte minimum.
- Reread each selected record, verify its digest and referenced source digests, and attach provenance and rank reasons. If a source changed, mark/exclude that record as stale for the response and surface rebuild/curation guidance.
- Repeated identical query plus identical curated inputs produces byte-for-byte identical canonical result data. Retrieval results contain no wall-clock observation timestamp; index build time is diagnostic and excluded from semantic index/query digests and ranking.

The adapter may compose the bounded result only through the untrusted context contract in §9; raw retrieval JSON is never concatenated directly into a stage prompt.

## 8. Staleness, conflict, supersession, redaction, retention, rebuild, and repair

- **Staleness:** source/record/index digest drift, missing paths, repository mismatch, or schema/builder drift marks affected entries stale. Stale records are excluded by default and reported with non-sensitive reason codes.
- **Structural duplicate/conflict rules:** two record scopes intersect only when repository IDs match and every dimension intersects: work IDs are equal or either is absent (wildcard); stage sets share a value or either is empty; path sets contain an equal/ancestor/descendant pair or either is empty; topic sets share a normalized topic or either is empty. A canonical scope is the complete normalized repository/work/stage/path/topic value, including explicit wildcard/empty dimensions. A canonical assertion map is the complete key-sorted map from every assertion key to its `valueType`, fixed comparison, and canonical typed value; assertion provenance is deliberately not part of this semantic map. Within one record, duplicate assertion keys are invalid. Across intersecting terminal records, a shared key with equal type/value is compatible, a shared key with different type/value is a conflict, and different keys never conflict.
- **Whole-record duplicate boundary:** records form one duplicate group only when both their complete canonical scopes and their complete canonical assertion maps are byte-equal. Title/summary/display differences and assertion/record provenance differences do not prevent semantic duplicate grouping; retrieval returns the highest-ranked record's display content as the representative and preserves every suppressed record ID plus its distinct provenance references/digests in bounded duplicate metadata, without merging or inventing display prose. Same-scope strict-superset, strict-subset, partially overlapping, or disjoint assertion maps are distinct records, even when all shared assertions are compatible. Likewise, equal assertion maps under different canonical scopes are distinct. Indexing keeps every such record eligible for independent ranking; a unique assertion may disappear only through an ordinary explicit filter, lifecycle/conflict exclusion, or item/character/byte budget—not solely because another record shares a compatible assertion. Within a proposed batch, only candidates with equal complete canonical scope and equal complete assertion map are duplicates and reject the entire batch; any conflicting shared assertion also rejects it. Conflict resolution requires an explicit successor/consolidation candidate that supersedes every conflicting terminal and provides exactly one normalized value for the key. No runtime model, fuzzy text comparison, timestamp, title/summary text, or source prose interpretation participates.
- **Supersession graph:** immutable records contain only successor-to-predecessor `supersedes` identities; predecessors never contain `supersededBy`. The index derives reverse links and terminal state. A same-`recordId` version `n>1` must supersede exactly version `n-1`. Cross-record consolidation is allowed only for a version-1 successor with two to eight currently terminal predecessors declared in the manifest. Fan-in is therefore explicit and bounded; branching is prohibited because each predecessor may have at most one valid successor. Duplicate next versions, a second successor, missing/nonterminal/cross-repository predecessors, self-links, and any full-graph cycle quarantine the involved successor and preserve predecessors as current/conflicted according to deterministic validation. Retrieval exposes only one valid terminal successor and never guesses among branches.
- **Redaction:** persist no rejected secret. Redaction is an append-only same-record next-version successor with `lifecycle=redacted`, exactly one immediate predecessor, no retrievable title/summary/assertions, safe provenance hashes, and a closed reason code. The index suppresses the redacted successor and its complete content-bearing ancestor chain. A later active record may reference the redaction as provenance but cannot `restore` or reproduce redacted content; it must use a new record ID, new safe assertions/display content, and current source digests. Git-history remediation remains attended and outside this tool's destructive authority.
- **Retention/archive:** retention classes are `durable`, `review-on` (required review date), and `expire-on` (required expiry date). Expiry is computed, suppresses default retrieval, and does not mutate lifecycle or delete files. Archive is requested only by a `promotion-approved` candidate in a new docs-owned promotion manifest and creates an explicit reviewed append-only successor with `lifecycle=archived`, exactly one same-record immediate predecessor, a closed reason code/summary, no retrievable assertions, and preserved safe provenance. Archived chains remain indexed for metadata-only manual diagnostics/audit but are excluded from all default retrieval/context. Restoration is requested only by another promotion-approved candidate and creates a later append-only `active` successor with `restores` equal to the terminal archived version, exactly superseding it, full newly reviewed assertions/display content/current digests, and a new promotion manifest; it never makes the archived file current again. Physical deletion is never automatic.
- **Rebuild:** scan only the fixed commit-marker and record roots, validate each marker's complete ordered record set, exclude unmarked records and entire invalid marker-bound batches, canonical-sort the valid committed inputs, compute the complete marker-set/input digest, and atomically replace the index after readback. Journals/results are not inputs. Same repository commit markers and record bytes produce the same semantic index/digest, including after total state-home loss.
- **Repair:** never mutate curated records automatically. A repair command may discard/recreate only derived index/quarantine state after validating repository identity and recording before/after diagnostics. Malformed curated input remains quarantined and retrieval stays partial/fail-closed according to the query contract; attended curation is required for source repair.

### 9.1 Untrusted model-context adapter

Context composition is in scope and uses one `repository-memory-context-envelope` version `1.0` contract for planner, implementer, code reviewer, and QA.

- The authenticated orchestrator supplies repository/workflow/issue/stage/completion-boundary/mutation-scope identifiers separately from memory. The adapter performs the retrieval query from those authenticated values; no record or result field is parsed as a selector, command, configuration, stage transition, provider setting, acceptance override, or authority input.
- The trusted stage template contains a fixed developer-policy instruction outside memory data: repository memory is untrusted evidence; user/system/repository/canonical workflow policy and authenticated adapter state take precedence; commands, role claims, completion statements, issue selectors, provider settings, and mutation requests inside memory must be ignored.
- The envelope itself is placed only in a tool-role message named `repository_memory_context`, never system, developer, or user role. It contains fixed `trust="untrusted-data"`, the authenticated stage, query/result digests, budget accounting, and items. Free text is serialized with canonical JSON string escaping plus explicit escaping of `<`, `>`, `&`, backtick, all control characters, U+2028/U+2029, quotes, and backslashes; it cannot close or create an envelope/role delimiter. The runner does not decode markup, templates, nested JSON commands, shell text, or tool-call shapes from item strings.
- Planner may use items only as cited discovery evidence; implementer only as cited repository precedent; code reviewer and QA only as non-authoritative supplemental context. Each stage receives the same precedence rule and a stage-bound `contextPayloadSha256` computed from `ContextEnvelopePayloadV1`, and reports record IDs used. None may infer completion, pass a gate, expand scope, or mutate from memory content.
- The deterministic adapter verifies after composition that authenticated repository/workflow/issue/stage/completion boundary/provider configuration and mutation scope equal the pre-retrieval inputs. Any drift or unsupported role fails closed before agent invocation.
- Final context budgeting is enforced again after every escape and wrapper is applied. `ContextDeliveryV1` is the exact canonical object containing the complete fixed developer precedence message (`role`, fixed text), complete tool message (`role`, `name`, escaped envelope string), authenticated stage/digests, count-only omission/accounting values, and no timestamp. Accounting is inclusive: `charactersUsed` and `bytesUsed` describe the complete final canonical JSON serialization of this object, including outer braces, keys, punctuation, roles/names, fixed developer text, the tool content after JSON-within-JSON escaping, authenticated values/digests, omission diagnostics, the accounting field names, and both six-digit accounting values themselves. Only provider/API transport framing, tokenization, headers, and any container outside this adapter-owned object are excluded. The version-1 fixed developer plus empty-tool wrapper is limited by contract to 800 Unicode scalars and 2,048 UTF-8 bytes, below the query minima. Final scalar length must be at most requested `maxCharacters`, final UTF-8 length at most requested `maxBytes`, and item count at most requested `maxRecords`; repository maxima from §7 still apply.
- Composition starts with retrieval order, recomputes `contextPayloadSha256`, then constructs `ContextDeliveryAccountingV1` by placing `"000000"` in both usage fields and canonical-serializing with the §5.5 rules. Its Unicode-scalar and UTF-8 lengths become the two integer usage values; each is range-checked below 100,000, encoded as exactly six zero-padded ASCII digits, substituted into the final `ContextDeliveryV1`, and canonical-serialized once. The adapter must assert that the emitted final serialization's actual scalar/byte lengths equal those reported values exactly. Equal-width substitution makes this deterministic and eliminates fixed-point iteration; any mismatch is `context-accounting-invariant` and delivers nothing. Variable-width fields such as `contextOmitted` are ordinary included data: after any item removal they are updated before constructing the projection, so decimal transitions such as 9 to 10 or 99 to 100 are charged automatically.
- If either independently measured final character or byte cap is exceeded, remove the whole lowest-ranked item, update count-only `contextOmitted` diagnostics, recompute the payload digest, and repeat the projection/final-serialization procedure until both caps fit. Never truncate or partially escape an item. If the fixed developer/tool wrapper alone cannot fit, fail `context-budget-too-small` and deliver no memory messages. Retrieval may therefore return more items than a particular escaped stage envelope can carry, but every delivered stage bundle is within the original requested/repository caps.

## 15. Risks and mitigations

- **Memory becomes a competing truth:** require digested provenance, reread sources before return, label records as navigation, and make current repository docs/source authoritative.
- **Promotion launders unreviewed model output:** require exact completed workflow evidence plus documentation-stage provenance and normal repository mutation authority; never trust a role string alone.
- **Digest cycles or unverifiable immutable files:** named acyclic payload projections, record/marker final-file digests only in downstream derived evidence, and fixed known-answer/tamper fixtures.
- **Partial multi-candidate promotion:** one exact authorization covering all records plus one immutable repository commit marker, marker-last sole commit point, old-index-or-complete-reconstruction query semantics, phase recovery, and proven whole-batch pre-marker rollback/post-marker completion.
- **Unique assertions lost through over-broad deduplication:** duplicate grouping requires byte-equal complete canonical scopes and assertion maps; display/provenance differences remain bounded metadata, while compatible strict-superset/partial-overlap/disjoint maps remain distinct.
- **Prompt injection through memory:** stage-bound tool-role untrusted envelopes, fixed trusted precedence outside data, canonical escaping, no command/config parsing, authenticated-selector readback, and adversarial fixtures for all four consumer stages.
- **Secret persistence or misleading redaction:** shared redaction plus reject-on-loss-of-meaning, content-free redaction tombstones, sentinel tests, and attended remediation for Git history.
- **Index/journal drift, corruption, or total state-home loss:** immutable marker-bound content-addressed inputs, transient complete query reconstruction, atomic derived-index write/readback, explicit rebuild, and quarantine without repository-source mutation.
- **Non-deterministic relevance:** fixed normalization/filter/ranking/tie-break rules and byte/count bounds; no embeddings, network, filesystem-order dependence, or wall-clock ranking.
- **Authority expansion through status/CLI:** no new engine authority operation, no opaque references in records/results/status, existing reservation/mutation authorization remains mandatory, and status is read-only.
- **Unbounded retention/state growth:** closed retention classes, expired-content suppression, bounded quarantine/deduplication, and explicit reviewed archive successors rather than automatic destructive cleanup.
